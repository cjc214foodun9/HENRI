The number states the whole defect

34359738368 bytes / 8 = 4,294,967,296 = 65536^2 = D x D

A D x D complex64 object at D=65536 is 32 GiB. The host has 31 GiB. The allocator refused with DefaultCPUAllocator: not enough memory. The host then page-thrashed.

The defect sat in two lines of the H3 harness:

base_cov.conj().transpose(0, 1) @ base_cov   # [D,64] @ [64,D] -> [D,D]

The fix computes a [64,64] Gram instead. The nonzero eigenvalues of X^H X equal those of X X^H. N=64 << D=65536, so the result is exact, not approximate.

Precise correction to the "never in VRAM" rule

Your stored corpus is never loaded whole. That part holds. But a per-step conditioning vector does cross into VRAM. production_arc_run.py:1843 runs recalled = _hits[0][0].to(DEVICE), then blends state_wave = 0.7*state_wave + 0.3*recalled. The same pattern appears at line 1437 for goal_wave.

That transfer is 256 KiB, not 32 GiB. So the rule you want is narrower than "never":

  • Never load the stored corpus whole. Already true.
  • Never form any [D, D] object. This is the 32 GiB crash. Fix landed (431845a).
  • Allowed to transfer a handful of individual 256 KiB engrams to condition one step.

Your constraint holds for the corpus

The write path calls .cpu(). The read path uses np.frombuffer on CPU. The 2000-dim HNSW index does the search. The full 65,536-dim BYTEA is fetched only for the top-k rows. That is the design you describe, and it is already in the code.
